# Assumptions

Every gap that had to be filled because `spec/` (Project Proposal = "Prop", Deliverable 1 = "D1") is silent or
ambiguous. Code comments reference these IDs.

A-n | what was missing | choice made | related spec section
---|---|---|---
A-1 | How the "Server" box (API gateway, auth gateway, 4 services, encrypted DB) is deployed; load balancing / telemetry details | One Spring Boot process with one package per box: `gateway` (API gateway + module routing), `security` (auth gateway), `controllers`+`services` (Social / Activity / Nutrition / Admin), PostgreSQL. Load balancing is not built for a laptop demo; telemetry = health checks + uptime records (FR-1). | D1 §5.3.1, §5.3.2, §5.3.3
A-2 | Which database product; Docker Engine not running on the build machine | PostgreSQL 16 (docker-compose) is the default. An `h2` Spring profile (embedded file DB, PostgreSQL mode) lets the app run and be tested without Docker. The same Flyway schema is used for both. | D1 §5.3.2 "Encrypted Database"; Prop §9 "Database for the app"
A-3 | How accounts are created (every use case includes "Log In" but there is no sign-up use case) | Students self-register (username, password, email, display name) and get a TOTP secret to add to an authenticator app. Developer accounts are created by seed/config only. | D1 Fig 4.3 "Log In (Password + TOTP)"; NFR Security
A-4 | Credential rules | Username 3–30 chars `[A-Za-z0-9_.]`, unique (case-insensitive); password ≥ 8 chars; email must look like an address. | NFR Security
A-5 | What "all user data will be encrypted" means concretely | Passwords: BCrypt hash. Email and TOTP secret: AES-256-GCM field encryption (key from `COMETFIT_DATA_KEY`). Other tables (meals, steps, …) rely on database/disk-level encryption in a real deployment, because the app must sum and query them. TLS is expected from the deployment's reverse proxy; the local demo uses plain HTTP. | NFR Security, NFR Legislative-Security; D1 §5.3.2 "Encrypted Database"
A-6 | Login flow detail and session lifetime | One login call carries username + password + 6-digit TOTP code; a Session (random 256-bit token, Bearer header) is created only if both factors pass, and lasts 12 h. `AuthService.authenticate` therefore takes the TOTP code as a third argument. TOTP = RFC 6238, SHA-1, 30 s, ±1 step. | D1 §5.2 AuthService, Session; NFR Security
A-7 | Default goals for a new student | 2000 kcal, 2000 ml water, 10 000 steps, 500 ml bottle. Students can change them. | D1 §5.2 Student (calorieGoal, waterGoalMl, stepGoal)
A-8 | Where the water-bottle size lives (Prop: "volume of the user's water bottle … number of refills"; SD-1 "log water (bottle size / refill)"; class diagram has no field) | Added `bottleSizeMl` to Student (set in Profile → Goals). The app logs a refill as `saveWaterEntry(bottleSizeMl)`, plus half bottle or a custom amount. | Prop §4; D1 SD-1
A-9 | What "daily" means (time zone of the day boundary) | Configurable `COMETFIT_ZONE`, default America/Chicago (D1 cites the Texas Data Privacy and Security Act, so the users are in Texas). | D1 UC-1 "View Daily Summary & Goals"
A-10 | Thresholds for an "unsafe goal" | Warn when calorie goal < 1200 or > 4000 kcal, water goal < 1000 or > 4000 ml, step goal > 30 000 (Prop risk "User over-exertion → Warnings of the app"). The goal is still saved; the app only warns (NFR says "allow a warning"). | D1 NFR Safety; Prop §8
A-11 | Which "portions of the app" can be shut down | Three modules, each mapped to an API prefix: NUTRITION (`/api/nutrition`), ACTIVITY (`/api/activity`), SOCIAL (`/api/social`). Login, profile and admin cannot be disabled. A disabled module answers 503 `MODULE_DISABLED`, and the client shows a maintenance notice on those tabs. | FR-5; D1 UC-4, SD-4 ("disable module (e.g. Friends)")
A-12 | How external systems (UREC card reader, monitoring service) authenticate | Shared secret in header `X-Integration-Key` (`COMETFIT_INTEGRATION_KEY`). Card readers must also be registered in `urec_card_readers`; seed reader `UREC-FRONT-1` at "UREC front desk". | D1 §5.3.2 External Systems; SD-2, SD-4; NFR Security
A-13 | Names and contents of the "backend permissions list" | Students implicitly hold `nutrition.use`, `activity.use`, `social.use`, `profile.use`. Developers hold an explicit list; the seeded developer has `admin.uptime.view`, `admin.modules.manage`, `profile.use`. Developers do not get student features. | D1 NFR Security; §5.2 Developer.permissions; UC-4 "Authorize Admin (Permissions + TOTP)"
A-14 | Data for a recorded demo | When `COMETFIT_SEED_DEMO=true` (default), seed developer `dev` and students `alice` and `bob`, password `CometFit123!`, with fixed, published TOTP secrets. Demo only; turn it off anywhere real. | PROMPT (demoable in a video)
A-15 | Behaviour of the "AI Food Recognition Service" | Stub: picks 1–2 entries from a fixed placeholder table, deterministically from the image's SHA-256. The estimate is shown for review and is saved only after the student confirms or edits it. The photo itself is not stored. | D1 UC-1 "Log Meal by Photo"; SD-1; Prop §2
A-16 | UTD Dining menu content and locations | Stub feed with two locations, "Dining Hall" and "Campus Store" (from FR-8's rationale "campus stores and dining hall"), and 5 placeholder items each. Each `getMenu` call refreshes items from the feed into `dining_items` (keyed by the feed's item id), so meal entries can reference them. | FR-8; D1 UC-1 "Maintain Dining Menu & Macros"; §5.2 DiningItem
A-17 | Meaning of `steps` in a pushed ActivityRecord | Steps counted since the previous sync (an increment). Daily steps = sum of the day's records. Limits per push: steps 0–100 000, heart rate 20–250 bpm. | D1 SD-2 "pushSteps(steps, heartRate, timestamp)"; §5.2 ActivityRecord
A-18 | Default data-sharing consent | All four `share*` flags default to false; nothing is visible to friends until the student turns it on. | D1 NFR Legislative-Privacy; §5.2 ConsentSettings
A-19 | When water intake is "too low" (FR-6 verification) | Any time today's total is below the student's water goal, the daily summary includes a "water intake is low" message. Reaching the goal shows a "goal reached" message instead. | FR-6 RTM verification method (D1 §4.4)
A-20 | Point values and limits | UREC visit: 10 points, awarded only for the first visit of each day (later swipes are still recorded). Reaching the daily step goal: 5 points, once per day. Points are never deducted. | Prop §3 "point based system"; D1 UC-2 "Earn Points", SD-2 `awardPoints(studentId, VISIT)`
A-21 | What the leaderboard ranks and who appears on it | Rank = point balance (ties share a rank), among the student and their friends. Points come only from visits and steps, so a friend appears (and their points show in their stats) only if they share visits or steps. | D1 UC-3 "View Leaderboard"; NFR Legislative-Privacy; Prop §7 leaderboard
A-22 | What `isPublic` controls | Non-friends viewing a private profile see only the username, not the display name or member-since date. Search by username always works, so friend requests are still possible. | D1 §5.2 User.isPublic; FR-3; Prop §4 "user-entered public information"
A-23 | How the friend is "notified of request" (Prop excludes push notifications) | In-app only: the request appears in the receiver's *Friend requests* list. | D1 SD-3 "notify of request"; Prop §4 Out of Scope
A-24 | Delivery channel for downtime alerts and when to send one | Stub `LoggingAlertNotifier`: logs a WARN line and keeps the last 50 alerts for the admin dashboard. An alert fires when a service goes down (first down check) and again when it recovers, not on every check. | D1 UC-4 "Raise Downtime Alert"; SD-4 alt [service down]
A-25 | Which "servers" are monitored, how often, how long records are kept | 7 components named after the §5.3.2 boxes (api-gateway, auth-gateway, nutrition-service, activity-service, social-service, admin-service, database), each with a real probe. Checks run every 30 s (configurable); uptime % is the share of successful checks over the chosen window (default 24 h). Records are kept 30 days. | FR-1; D1 SD-4 loop [every interval]; §5.2 MonitoringService.checkIntervalSec
A-26 | Client technology, given "mobile app only, no web application" (Prop §4, §7) vs. the requirement that the demo runs in a browser | Cross-platform Expo / React Native app (NFR Development: "native or cross-platform mobile app"). The same app is run through react-native-web for the laptop demo; this is a way to run the mobile client, not a separate web product. The phone-sized layout is kept. | Prop §4 Out of Scope; D1 NFR Operational, NFR Development; PROMPT
A-27 | What the UREC card carries to identify the student | The card reader sends the student's CometFit user id as `studentId` (the class diagram has no separate card-number field). | D1 SD-2 `recordVisit(studentId, time)`; §5.2 UrecCardReader.sendSwipe(studentId)
A-28 | Smart-device link rules | A health-data permission must be granted before linking (UC-2 «include» Grant Health Permissions). A device can be LINKED to only one student at a time. Unlinking keeps history. In the browser, the OS permission prompt and the wearable are simulated (client `FakeSmartDevice`). Optional automatic sync runs every 60 s while the Activity screen is open. | D1 UC-2, SD-2; NFR Interoperability
A-29 | Editing or deleting logged meals, water or visits | Not provided; the spec only describes logging and viewing. | D1 UC-1, UC-2
A-30 | Range of friend statistics | A friend's stats show today's calories, water and steps (with goals), UREC visits in the last 7 days, point balance, and leaderboard rank, each only if consented. | D1 UC-3 "View Friend's Statistics"; SD-3
A-31 | Brute-force protection and rate limiting | Not implemented (out of scope for the course prototype). The login error message is the same for every failure, so usernames can't be probed. | D1 NFR Security
A-32 | Visual design (Figma designs are not in `spec/`) | Simple neutral card-based layout with a bottom tab bar (Today, Log, Activity, Friends, Profile) and a separate admin dashboard for developers. | D1 NFR Development ("Figma for design"); NFR Usability
